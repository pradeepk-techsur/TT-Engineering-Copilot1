<objective>
Fix the three linked blockers that prevent phase execution from completing end-to-end:

1. **xlsx bundling failure** — `XLSX.writeFile()` uses `fs.writeFileSync` internally but Next.js App Router bundles `xlsx` without `fs` module access (standard webpack server-side bundling restriction). Fix: add `serverExternalPackages: ['xlsx']` to `next.config.mjs` so Next.js loads `xlsx` from `node_modules` at runtime instead of bundling it. As a belt-and-suspenders fix, also rewrite `generateXlsx()` to use `XLSX.write(wb, {type:'buffer'})` + native `writeFileSync` (the same pattern that works for DOCX) instead of `XLSX.writeFile()`.

2. **Duplicate artifact_registry rows** — DOCX writes succeed and insert to `artifact_registry` on each partial run, causing constraint issues on retry. Fix: delete stale `AgentGenerated` rows for the same `(phaseId, gateId)` before inserting new ones inside `generateXlsx()` and `generateDocx()`.

3. **Silent Run Phase button** — The "Run Phase" button's `onClick` is a no-op comment. The user clicks it and nothing happens because the handler was left as a stub. Fix: implement the `onClick` to POST to `/api/phases/{phaseId}/execute`, show a spinner during execution, surface any error in the UI, and trigger SWR revalidation on success.

Purpose: UAT blockers 1, 4, and 5 all share this root cause. After this fix, phases 0, 1, and 2 execute end-to-end and produce their compact artifacts.
Output: Updated `next.config.mjs`, `artifactGenerator.ts`, and `InputReadinessPanel.tsx`.
</objective>

const handleRunPhase = async () => {

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | Phase workspace browser client POSTing to /api/phases/{id}/execute — no body payload from client (execute routes read phaseId from path only) |
| api→filesystem | Agent-generated XLSX/DOCX bytes written to `outputs/` directory on the server filesystem via writeFileSync |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Elevation of privilege | `InputReadinessPanel.tsx` → `/api/phases/${phaseId}/execute` | mitigate | `phaseId` is typed as `number` from the server-rendered prop (`phaseId: number`), sourced from route params already validated against `PHASE_CONFIG_MAP` in the page component — not from any user-controlled form field. The fetch URL uses the server-injected numeric `phaseId`, not any client-side string. The execute route itself validates inputs-ready state before running the agent. |
| T-03-02 | Tampering / Path traversal | `getStorageDir(phaseId)` in `artifactGenerator.ts` | mitigate | `phaseId` is a `number` (TypeScript) passed from the API route which validates it is an integer 0–9 before calling the agent. `path.join(process.cwd(), 'outputs', projectId, 'phase${phaseId}')` cannot traverse because `phaseId` is already a bounded integer, not a string with `..` sequences. |
| T-03-03 | Denial of service | `generateXlsx` / `generateDocx` delete-then-insert on every execute | accept | Delete targets `(phaseId, gateId, source='AgentGenerated', generatedBy, artifactType)` — a bounded, indexed set. In the POC there is one project and ≤2 rows per phase; the delete is trivially fast. Residual risk: a sufficiently large production dataset could make the delete slow; owner: platform team before any production use. |
| T-03-04 | Information disclosure | `executeError` state rendered in browser | mitigate | Error message comes from `data.message ?? data.error_code` returned by the server API. The API routes only return the error message string and error_code enum (e.g. `AGENT_FAILED`) — no stack traces, no internal paths, no DB details are included in the 500 response shape in `src/app/api/phases/*/execute/route.ts`. |
</threat_model>
