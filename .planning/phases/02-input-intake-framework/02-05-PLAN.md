**Root cause (confirmed in debug session):** Rules 3 and 4 call `firstSheet.flat()` to produce a 1D array, then use `.findIndex(c => c.includes('Project ID'))` and `.includes('Product')`. In a typical EV inventory XLSX, data-table column headers like "Product Name" and "Project ID" appear in earlier rows (lower flat-array index) than the metadata rows. `findIndex` returns the column-header match, and `allCells[idx+1]` returns the next column header (e.g., "Quantity") — not the actual metadata value — triggering false MISMATCH errors on valid files. Additionally, Rule 4 line 73 hardcodes `'EV-INV-800'` instead of using `config.productName`.

**Fix: add `findMetadataValue()` helper and replace Rules 3 and 4:**

In `src/server/intake/fileValidator.ts`, add this helper function immediately before `validateUploadedFile`:

```typescript
/**
 * Searches rows for a metadata label in col A or col B (index 0-1) using
 * exact case-insensitive equality, then returns the value in the adjacent cell
 * (same row, next column). Ignores data-table column headers that only partially
 * match (e.g. "Product Name" will NOT match exactLabel "Product").
 */
function findMetadataValue(rows: unknown[][], exactLabels: string[]): string {
  for (const row of rows) {
    const cells = (row as unknown[]).map(c => String(c ?? '').trim());
    // Only check leading columns (index 0 and 1) — metadata labels are always in col A or B
    for (let i = 0; i <= Math.min(1, cells.length - 2); i++) {
      if (exactLabels.some(label => cells[i].toLowerCase() === label.toLowerCase())) {
        return cells[i + 1] ?? '';
      }
    }
  }
  return '';
}
```

**Note on Rule 4 exact labels:** `'Product Name'` IS included as an exact label because some files use "Product Name" as the metadata label. The helper checks `cells[i].toLowerCase() === label.toLowerCase()` — exact equality — so a column header also named "Product Name" IN THE SAME ROW would match. However, this is correct behavior: if the label IS "Product Name" in col A, we read col B as the value. The critical fix is that "Product Name" in col D (index 3+) of a data-table header row is excluded because we only check `i <= 1` (col A and B).

|-----------|----------|-----------|-------------|-----------------|
| T-02-05-01 | Tampering | `fileValidator.ts::findMetadataValue` — row-iterating cell reader | mitigate | `findMetadataValue` reads only `cells[i]` and `cells[i+1]` within bounds (`i <= Math.min(1, cells.length - 2)`), preventing out-of-bounds reads. All cell values are coerced with `String(c ?? '').trim()` — no eval, no dynamic key access, no prototype pollution path. Label matching uses `.toLowerCase() === label.toLowerCase()` strict equality, not `eval` or regex with user input. Validation occurs in `validateUploadedFile` in `src/server/intake/fileValidator.ts` before any DB write. |
| T-02-05-02 | Denial of service | Large XLSX with many rows processed by `findMetadataValue` | accept | `findMetadataValue` iterates all rows but exits on first match (early return). Existing Rule 6 (ROW_COUNT_WARNING) alerts on >10 rows — files are expected to be small. No recursive or exponential logic. For POC scale, linear scan over small XLSX is acceptable. Residual risk: accepted by POC design decision (no upload size hard limit beyond framework guidance). |
| T-02-05-03 | Spoofing | Attacker crafts metadata rows with injected labels to bypass validation | mitigate | `findMetadataValue` uses exact-equality (`===`) on trimmed strings — substring injection cannot cause false acceptance. A metadata row with label "Project ID" and wrong value still fires PROJECT_ID_MISMATCH. The fix only prevents false positives (wrong column-header matches); correct rejection behavior is preserved and regression-tested in `tests/intake.test.ts::fires PROJECT_ID_MISMATCH when metadata row has wrong project ID`. |
